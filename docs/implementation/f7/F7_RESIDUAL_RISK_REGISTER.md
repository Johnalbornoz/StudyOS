# F7 — Assessment Framework Engine — Residual Risk Register

Date: 2026-09-18. Scope: risks that remain after F7 Preview certification. None of these block Preview; several explicitly gate Production/pilot readiness (see F7_NEXT_PHASE_HANDOFF.md).

| # | Risk | Severity | Where it lives | Mitigation status |
|---|---|---|---|---|
| R1 | The Full Mock Guard (`canFullMockBeOffered`) only reports readiness — it does not, and per task §31 must not, build the actual mock-exam simulator. A real learner cannot yet take a Full Mock even when the guard reports `ready: true`. | High (scope, not defect) | `src/lib/assessment/full-mock-guard.service.ts` | By design — deferred to a future phase; do not interpret `ready: true` as "simulator exists" |
| R2 | Item generation for exam contexts (`resolveGenerationContext` + `validateItemForExamContext`) has no live AI-generation call wired to a real exam attempt yet — the contract and validation exist and are certified, but nothing in F7 invokes an LLM to author an exam item end-to-end. | Medium | `src/lib/assessment/generation-contract.service.ts`, `validation.service.ts` | Contract-level only; real generation wiring is future-phase work |
| R3 | `approved_items`/`approved_item_families` workflow (DRAFT→...→PUBLISHED) has no populated content — the pilot dataset does not seed any approved items, so the item bank is structurally certified but empty in every environment including Preview. | Medium | `database/migrations/20260925_1000_f7_assessment_framework_engine.sql`, `item-bank.service.ts` | Expected at this phase; population is a content-authoring workstream, not an engineering one |
| R4 | Institution Exam Policy verification (`verifyPolicy`) has no real-world verification workflow behind it (e.g. document upload, human review, external registrar confirmation) — `verifyPolicy` is currently a direct state transition callable by any admin. | Medium | `src/lib/assessment/institution-policy.service.ts` | Acceptable for Preview; a real verification workflow (who verifies, on what evidence) is undesigned and must precede any pilot claim of "verified" institution policy |
| R5 | Only one Admission Exam vertical (PAA) and one contrast vertical (Cambridge IGCSE) have been exercised. No IB, SAT, or other exam family has been configured even as a smoke test — the "one configurable engine, not per-family bespoke engines" invariant (task's core architectural goal) is proven for 2 families, not validated at broader scale. | Medium | Pilot dataset (`f7-seed-pilot-dataset.ts`) | The schema itself carries no PAA/Cambridge-specific branching (verified by INV-F7 non-interference tests), so the risk is one of *unexercised* breadth, not hidden coupling — but breadth should be proven before claiming general readiness |
| R6 | `exam_attempts.frozen_configuration` is a `jsonb` snapshot with no schema/version tag inside the JSON itself. If the shape of what gets frozen changes in a future phase, there is no migration path for historical frozen snapshots to be reinterpreted safely. | Low | `database/migrations/20260925_1000_f7_assessment_framework_engine.sql` | Low likelihood near-term; flagged for whoever next changes `startExamAttempt`'s snapshot shape |
| R7 | The evidence bridge (`bridgeExamResponseToEvidence`) requires the caller to already know the per-student `conceptId` corresponding to the canonical `learningObjectiveId` — there is no automatic resolution, by design (per Problem Solving decision in this phase). Any future caller that does not already have this correspondence will silently be unable to bridge evidence unless it independently resolves it via F4's mapping service first. | Low (by design, but a footgun for future integrators) | `src/lib/assessment/evidence-bridge.service.ts` | Documented in `F7_EVIDENCE_BRIDGE.md`; worth an explicit runtime guard/error message in a future hardening pass rather than silent no-op |
| R8 | No load/performance testing was performed against the new tables (`exam_attempts`, `exam_attempt_item_responses` in particular, which will be write-heavy under real exam-taking traffic). | Low | N/A (untested) | Deferred — no real traffic exists yet since the simulator (R1) doesn't exist |
| R9 | The two Vercel MCP/Neon integrations available in this environment require interactive OAuth and were not used; all migration certification was performed against ephemeral local Postgres per task §45's explicit allowance ("real database migration certification against local ephemeral Postgres when remote isolation can't be proven"). Preview's actual remote database was not migration-tested in this phase. | Medium | Deployment process | Consistent with F1–F6 precedent; the actual Preview/Neon database's migration state should be confirmed before any pilot use of `/api/admin/assessment/*` against real Preview data |

## Explicitly out of scope for F7 (not risks — deliberate non-goals per the task spec)

- Building the Full Mock simulator UI/flow (R1 above documents the guard exists, the simulator does not).
- A pedagogical-stage-changing consequence of assessment scoring (explicitly forbidden by INV-F7-01/02/20 and verified never to occur).
- A second pedagogical progression authority (explicitly forbidden; verified via non-interference tests).
- Any Production deployment or Production environment variable change.
