# STUDYUS — CANONICAL POLICY V2 — FULL AUDIT / CERTIFICATION

**Mode:** AUDIT ONLY. No production code was modified. No fixes were implemented. Branch `tmp/lx1`. Production and `main` untouched.

## EXECUTIVE SUMMARY

**Certification verdict: FAIL.**

The pure pedagogical engine (`src/lib/pedagogical-engine/`) correctly implements roughly two-thirds of Policy V2 — LEARN, the PROVE contract and rollback, RETAIN's temporal gate and novelty requirement, TRANSFER's per-challenge-floor-plus-overall-average check and its Case A/C/D rollback directions, and the global critical-misconception override — and every one of those areas is now covered by real, passing, executable tests. However, the audit found **four BLOCKER-severity gaps**, each directly contradicting an explicit, numbered rule in the frozen policy, plus two P1-severity gaps and two documented specification ambiguities:

1. **AUDIT-001 (BLOCKER):** PRACTICE has no "2 of last 3" consistency window — a single qualifying attempt still satisfies PRACTICE and unlocks PROVE, exactly the CANON-R2-era rule the frozen V2 policy explicitly supersedes.
2. **AUDIT-002 (BLOCKER):** RETAIN has no two-strike counter — the very first Retention failure immediately rolls back to PROVE, denying the policy-mandated "immediate second attempt, new questions, no wait" and instead forcing a full Prove rebuild.
3. **AUDIT-003 (BLOCKER):** TRANSFER's failure classification has only 3 buckets, not the policy's 4 — there is no "Case B: retention weakness → rollback to RETAIN" at all, structurally (no signal field, no rollback case, no code path).
4. **AUDIT-004 (BLOCKER):** the legacy migration/backfill layer (`evaluateLegacyRecognition`) can fabricate PROVE/RETAIN/TRANSFER "satisfied" recognition purely from old, pre-cutover mastery-dimension scores, with zero real v1 evidence — directly contradicting the frozen policy's "higher stages must not be fabricated." **Mitigating fact, independently verified:** the backing table and the one CLI that would write these rows have never been executed against any real environment (self-documented in their own headers) — no real student data is corrupted by this path today, but the code is a live landmine the moment that CLI is ever run with `--apply`.

Additionally: **AUDIT-005 (P1)** — per-attempt critical-misconception detection is structurally dead in production (the real evidence-fetch query never selects a source column for it), leaving only the coarser, global "is any misconception currently active" flag as a working safeguard; and **AUDIT-006 (P1, needs verification)** — the UI module that names itself "the single canonical learning-progress read model" has zero wiring to the new canonical engine, unlike ConceptMission and Today, which both correctly apply a One-Authority-Rule override.

**Critical context for interpreting every finding above:** `isCanonicalEngineV1Enabled()` is a hard interlock that returns `false` unconditionally whenever `VERCEL_ENV === 'production'`, regardless of any configuration value. **The entire canonical engine — and therefore every rule audited here, correct or broken — is not live for real Production users today.** It activates only in a non-production environment with an explicit `CANONICAL_ENGINE_V1_ENABLED=true` flag. This does not reduce the severity of the findings (they must all be fixed before the gate is ever flipped on in Production) but it does mean no real learner is currently affected by AUDIT-001/002/003, and — per the point above — AUDIT-004 has not yet touched real data either.

## DETAILED FINDINGS

### AUDIT-001 — PRACTICE "2 of last 3" consistency rule is entirely unimplemented

- **Subsystem:** Pedagogical Engine — `src/lib/pedagogical-engine/engine.ts` (`replay`, PRACTICE branch, lines ~206–225).
- **Rule violated:** Policy V2 §3 — "PRACTICE is satisfied only when AT LEAST 2 OF THE LAST 3 VALID PRACTICE ATTEMPTS have score ≥ 80% AND there is no active critical misconception."
- **Current behavior:** `practiceSatisfied` is set to `true` (and stays sticky) the moment **any single** Practice attempt qualifies (`qualifyEvidence` returns `QUALIFIES`). There is no window, no counting, no "2 of last 3" logic anywhere in the codebase (confirmed by grep for `consecutiveFailure`/`attemptNumber`/`retainAttempt`/similar — none exist).
- **Expected behavior:** PRACTICE must remain UNSATISFIED until a sliding window of the last (up to) 3 valid Practice attempts contains at least 2 passing (≥80%) attempts.
- **Evidence:** `src/lib/pedagogical-engine/engine.ts:206-225`; `tests/unit/audit-canon-v2-practice-consistency.test.ts` — 7 failing tests, including the policy's **own verbatim worked example** `[100,40,40] → UNSATISFIED` (current: SATISFIED) and the cleanest isolated proof: a single 100% Practice attempt, alone, currently satisfies PRACTICE and unlocks PROVE.
- **Severity:** BLOCKER.
- **Likely root cause:** this is CANON-R2's original design (single-qualifying-attempt = satisfied), predating Policy V2's consistency requirement; the engine was never updated for this specific V2 rule.
- **Affected transitions:** PRACTICE→PROVE unlock (premature in ~40% of realistic score sequences, per the boundary matrix); PROVE-failure requalification (§5, "learner must requalify PRACTICE again... AT LEAST 2 OF LAST 3 VALID PRACTICES ≥80%" — currently requalifies on the very next single pass).
- **Existing data corrupted?** N/A directly (the engine is not live in Production — see Executive Summary); if the flag were ever flipped on in Preview/dev today, learners there would be allowed into PROVE prematurely.
- **Remediation scope estimate:** Medium. Requires: (a) a "valid Practice attempt" filter (already partially expressible via existing qualification checks for activity type/difficulty/contract), (b) a sliding-window-of-3 evaluator over valid attempts, (c) resolving AUDIT-001-AMBIGUITY (does the window reset on rollback?) with product before implementing, (d) updating `resolvePracticeDifficulty`'s own evidence-selection comment if the difficulty rule is meant to use the same window (currently it does not need to — difficulty already only cares about the single most recent attempt).
- **Recommended regression tests:** all of `tests/unit/audit-canon-v2-practice-consistency.test.ts` (already written, currently red where they must go green after remediation) plus the intentionally-unasserted "invalid attempt inserted between valid attempts" and "Reinforce active vs inactive" cases from Section 18, once the window logic exists to test against.

### AUDIT-002 — RETAIN has no two-strike rule; any single failure rebuilds Prove

- **Subsystem:** Pedagogical Engine — `src/lib/pedagogical-engine/engine.ts` (RETENTION_CHECK failure branch, lines ~276–293).
- **Rule violated:** Policy V2 §6 — "Retain Attempt 1 FAIL → second Retain opportunity is available immediately... no additional 3-day wait. SECOND CONSECUTIVE RETAIN FAILURE → rollback to PROVE."
- **Current behavior:** Any single `RETENTION_CHECK` `FAILED_ATTEMPT` immediately resets `proveSatisfied=false` and `proveQualifyingAt=null`, rolling back to PROVE. A second Retain attempt submitted afterward evaluates with `prerequisiteSatisfied = proveSatisfied = false` and is rejected as `PREMATURE_STAGE_EVIDENCE` — it **cannot qualify even with a passing score**, forcing a full Prove rebuild instead of the policy-mandated immediate second chance.
- **Expected behavior:** the first failure must not touch PROVE at all; only a **second consecutive** failure should trigger the PROVE rollback.
- **Evidence:** `src/lib/pedagogical-engine/engine.ts:276-293`; `tests/unit/audit-canon-v2-retain-two-strike.test.ts` — the sequence "Retain fail (50%), Retain pass (90%, same day)" currently reports RETAIN=LOCKED, PROVE=UNSATISFIED (should be RETAIN=SATISFIED, PROVE=SATISFIED, stage=TRANSFER).
- **Severity:** BLOCKER.
- **Likely root cause:** the engine has no per-cycle attempt counter of any kind (confirmed absent by source audit — no `retentionContext`/`attemptNumber` field exists anywhere, despite `rebuildConceptCanonicalState`'s own doc comment mentioning a `retentionContext` parameter that was apparently never actually built into the accepted signature).
- **Affected transitions:** RETAIN retry-after-failure (this is the single most damaging concrete consequence in the whole audit: a learner who should get a free, immediate second attempt instead loses their qualified Prove and must fully re-earn PRACTICE→PROVE before they can even attempt RETAIN again).
- **Existing data corrupted?** N/A — engine not live in Production.
- **Remediation scope estimate:** Medium. Requires threading a "how many consecutive Retain failures since the last qualifying Prove" counter through the replay (naturally derivable by counting `RETENTION_CHECK` `FAILED_ATTEMPT` items since the last qualifying `PROVE` item, without any new engine input field), and changing the rollback trigger from "any failure" to "second consecutive failure."
- **Recommended regression tests:** `tests/unit/audit-canon-v2-retain-two-strike.test.ts` (already written); add, once built: a test confirming an intervening *qualifying* Prove resets the strike counter to zero for the new cycle (per §6's "new PROVE PASS → new 3-day window starts from zero").

### AUDIT-003 — TRANSFER has only 3 failure classifications, not 4; Case B (retention-weakness → RETAIN) does not exist

- **Subsystem:** Pedagogical Engine — `src/lib/pedagogical-engine/types.ts` (`RollbackCase`), `engine.ts` (TRANSFER failure branch, lines ~331–365).
- **Rule violated:** Policy V2 §7 — Case B: "Failure indicates retention weakness, while underlying Prove remains valid → rollback to RETAIN → RETAIN may be re-attempted immediately → DO NOT wait 3 days again."
- **Current behavior:** the closed `RollbackCase` union has exactly 5 members: `PROVE_FAILURE_RETURN_TO_PRACTICE`, `RETENTION_FAILURE_RETURN_TO_PROVE`, `CASE_A_TRANSFER_APPLICATION_WEAK`, `CASE_B_FOUNDATIONAL_FAILURE`, `CASE_C_CRITICAL_MISCONCEPTION`. None targets RETAIN. The engine's own `CASE_B_FOUNDATIONAL_FAILURE` (triggered by `transferFoundationalFailureIndicated: true`) actually corresponds to the policy's **Case C** (foundational failure → PRACTICE), not the policy's Case B. There is also no `RawEvidenceItem` field to even express "this failure indicates retention weakness" as distinct from "foundational failure."
- **Expected behavior:** a fourth, distinct classification that rolls back only to RETAIN, with immediate-retry-no-wait semantics (closer to the existing RETAIN-failure-strike-1 behavior once AUDIT-002 is fixed, but triggered from TRANSFER instead of from RETAIN itself).
- **Evidence:** `src/lib/pedagogical-engine/types.ts:205-210`; `tests/unit/audit-canon-v2-transfer-classification.test.ts` — source-level proof that the union has no RETAIN-targeting member and no distinct signal field exists.
- **Severity:** BLOCKER.
- **Likely root cause:** CANON-R2R1's own historical decision explicitly built only 3 diagnoses (documented in `engine.ts`'s own comments: "PROVE_FAILURE/RETENTION_FAILURE follow simple undiagnosed rules; the three CASE_* diagnoses are reserved for TRANSFER"), predating Policy V2's introduction of a 4th, RETAIN-targeting case.
- **Affected transitions:** any Transfer failure that should be diagnosed as retention-weakness is currently forced into either Case A (stay Transfer, if no foundational signal is set) or Case C (rollback all the way to PRACTICE, if a foundational signal happens to be set) — never the correctly-scoped RETAIN-only rollback.
- **Existing data corrupted?** N/A — engine not live in Production; also, real Transfer evidence today has no per-challenge breakdown at all (`TRANSFER_CHALLENGE_BREAKDOWN_UNAVAILABLE`, confirmed in the evidence adapter), so this branch is not yet reachable with real data regardless.
- **Remediation scope estimate:** Medium-High — needs a product decision on what real, non-score-based signal distinguishes "retention weakness" from "foundational failure" (both are currently gated by the same kind of external diagnostic input this isolated engine cannot compute itself), a new `RawEvidenceItem` field, a new `RollbackCase` member, and new engine branch logic plus a `RollbackDecision.rolledBackTo: 'RETAIN'` path.
- **Recommended regression tests:** `tests/unit/audit-canon-v2-transfer-classification.test.ts` (already written) plus new tests once the field/case exist, confirming (a) RETAIN itself becomes immediately re-attemptable with no wait, and (b) PROVE remains untouched (unlike Case C, which currently invalidates PRACTICE and locks PROVE/RETAIN too).

### AUDIT-004 — Legacy migration recognition can fabricate PROVE/RETAIN/TRANSFER satisfaction from old mastery scores alone

- **Subsystem:** Migration compatibility layer — `src/lib/pedagogical-migration/legacy-recognition.ts` (`evaluateLegacyRecognition`, lines 90-106), `migration-baseline.ts`, `scripts/canon-r4r1-pre-v1-learn-baseline.ts`.
- **Rule violated:** Policy V2 §14 — "Pre-cutover concepts may receive LEARN through LEGACY_MIGRATION_BASELINE. **Higher stages must not be fabricated.**"
- **Current behavior:** `evaluateLegacyRecognition` grants `PROVE`/`RETAIN`/`TRANSFER` `SATISFIED` recognition (basis `LEGACY_POLICY_RECOGNITION`) purely from the OLD `ConceptKnowledgeState`'s dimension scores (`independenceScore`, `retentionScore`, `applicationScore`, `transferScore` vs. `MasteryPolicy` thresholds) — with `sourceEvidenceIds: []` in every case, i.e. **zero backing real evidence of any kind**. The one CLI that computes and can persist this (`scripts/canon-r4r1-pre-v1-learn-baseline.ts`), despite its own name and log banner ("Pre-v1 LEARN Baseline"), passes `baseline.recognizedRequirements` **unfiltered** to `applyRecognitions` — it does not restrict the write to LEARN only, and its own dry-run output explicitly tracks `higherLegacyCounts: { PRACTICE, PROVE, RETAIN, TRANSFER }` as a first-class metric, confirming this is a known, exercised code path, not a theoretical one.
- **Expected behavior:** a pre-cutover migration baseline may only ever recognize LEARN automatically; PROVE/RETAIN/TRANSFER must require real v1 evidence, full stop.
- **Evidence:** `src/lib/pedagogical-migration/legacy-recognition.ts:90-106`; `scripts/canon-r4r1-pre-v1-learn-baseline.ts:104-145`; `tests/unit/audit-canon-v2-legacy-fabrication.test.ts` (6 passing tests proving the capability end-to-end, including feeding the fabricated recognitions straight through `evaluateCanonicalLearningState` and observing `stage: 'CONSOLIDATED'` for a concept with **zero** `learning_evidence` rows).
- **Severity:** BLOCKER.
- **Likely root cause:** `evaluateLegacyRecognition` predates CANON-R4R1's later, narrower "LEARN-only automatic baseline" decision (documented in `migration-baseline.ts`'s own comments as "the FINAL, one-time migration exception... ONLY LEARN") — the higher-stage cascading-ladder logic in `legacy-recognition.ts` was seemingly never actually removed or gated off after that later, narrower policy decision was made, and the CLI built afterward (`canon-r4r1-pre-v1-learn-baseline.ts`) still calls the full, unnarrowed function.
- **Affected transitions:** any pre-cutover concept with strong legacy mastery scores could be granted instant PROVE/RETAIN/TRANSFER/CONSOLIDATED status with no real v1 canonical evidence, the moment this recognition is computed and persisted.
- **Existing data corrupted?** **Verified: NO, not yet.** Both `database/migrations/20260915_1000_canon_r4r1_pedagogical_requirement_recognition.sql` (the backing table) and `scripts/canon-r4r1-pre-v1-learn-baseline.ts` (the only writer) explicitly, self-documentedly, have never been executed in any environment (confirmed via their own header comments — no live DB access exists in this session to independently verify against a real database, but no code path in this repository has ever called `applyRecognitions` outside this one script, and this script has never run).
- **Remediation scope estimate:** Low-to-Medium. Either (a) narrow `evaluateLegacyRecognition` itself to only ever return a LEARN recognition (deleting or gating off the PRACTICE/PROVE/RETAIN/TRANSFER cascading branches), or (b) filter `baseline.recognizedRequirements` to `requirement === 'LEARN'` at the CLI's own call site before `applyRecognitions`. Given the function's own name (`evaluateLegacyRecognition`, generic) versus the CLI's own name (explicitly "LEARN Baseline"), option (b) is the more surgical, lower-blast-radius fix, but option (a) is more defensible long-term since it removes the fabrication capability at its source rather than only at one call site — **this decision should be made in the remediation phase, not silently here.**
- **Recommended regression tests:** `tests/unit/audit-canon-v2-legacy-fabrication.test.ts` (already written; should be updated to assert the NEGATIVE — that higher-stage recognitions are never produced/applied — once remediated) plus a dedicated CLI-level test asserting `applyRecognitions` is never called with a non-LEARN requirement from this script.

### AUDIT-005 (P1) — Per-attempt critical-misconception detection is structurally dead in production

- **Subsystem:** Evidence pipeline — `src/lib/pedagogical-shadow/evidence-fetch.ts` (`fetchStudyUSEvidenceRows`), `evidence-adapter.ts`.
- **Rule violated:** Policy V2 §9 (partially) — the per-attempt dimension of "a critical misconception detected during this specific attempt" cannot be observed from real data.
- **Current behavior:** `fetchStudyUSEvidenceRows`'s SQL selects no misconception-related column at all; `StudyUSEvidenceRow.hasItemCriticalMisconception` is therefore always `undefined`, and `evidence-adapter.ts` defaults it to `false` for every real row. `qualifyEvidence`'s `if (item.hasCriticalMisconception) return DOES_NOT_QUALIFY` branch, and `resolvePracticeDifficulty`'s own misconception-driven difficulty decrease, are consequently unreachable with real data.
- **Expected behavior:** either this capability should be genuinely wired to a real per-attempt misconception link, or the frozen policy/engine should be understood to rely solely on the GLOBAL `activeCriticalMisconception` flag for this purpose (which IS correctly wired and IS sufficient to satisfy Policy V2 §9's actual blocking requirement — see below).
- **Evidence:** `src/lib/pedagogical-shadow/evidence-fetch.ts:42-65` (SELECT clause); `src/lib/pedagogical-migration/new-evidence-capture-contract.ts:56` (the field is explicitly documented there as a future, unwired capture contract — this is a KNOWN, DELIBERATE gap, not a silent regression); `tests/unit/audit-canon-v2-learn-prove-misconception.test.ts` (AUDIT-005 describe block).
- **Severity:** P1 (not BLOCKER) — mitigated because the GLOBAL flag mechanism, independently verified, correctly satisfies the policy's actual headline requirement ("an ACTIVE critical misconception blocks advancement... must remain blocking until later qualifying evidence explicitly resolves it... score alone must never clear it") via `misconception.service.ts`'s `isMisconceptionResolutionEvidence`, which requires dedicated EXPLANATION or SOLO_VERIFICATION evidence, unassisted — never an ordinary high quiz score.
- **Likely root cause:** documented, intentional deferral (`new-evidence-capture-contract.ts` is explicitly a "data contract only... nothing wired into any generation route... in this phase").
- **Affected transitions:** none currently observable in practice (the coarser global override compensates), but the *nuance* the policy implies — a specific attempt being individually disqualified for its own misconception, vs. the whole journey being globally blocked — cannot be exercised.
- **Existing data corrupted?** No — this is an absence-of-capability, not an incorrect computation.
- **Remediation scope estimate:** Medium — requires linking a specific `learning_evidence` row to the `student_misconceptions`/`misconception_signatures` detection event it triggered (schema/data-model work), then adding that column/join to `fetchStudyUSEvidenceRows`.
- **Recommended regression tests:** once wired, a test confirming a real per-attempt misconception flag correctly rejects that specific attempt via `CRITICAL_MISCONCEPTION`, independent of the global flag.

### AUDIT-006 (P1, needs verification) — `canonical-learning-progress.ts` has no wiring to the canonical engine

- **Expected behavior:** unclear without further tracing — see below.
- **Evidence:** `src/lib/lx/canonical-learning-progress.ts` (full file, no canonical imports); `src/services/concept-mission-view.service.ts:214-230` and `src/services/learning-os-snapshot.service.ts:192-210` (the correct override pattern, for contrast); `tests/unit/audit-canon-v2-feature-gate-and-ui-authority.test.ts` (AUDIT-006 describe block).

- **Affected transitions:** potentially My Path / Subjects concept-row display, if (a) is the case.
- **Existing data corrupted?** N/A (display-only; even if (a), the engine is not live in Production today).

- **Recommended regression tests:** a source-audit test locating every caller of `buildCanonicalLearningProgress` and asserting each either (i) also calls `getCanonicalPedagogicalDecision`/`isCanonicalEngineV1Enabled` in the same request path, or (ii) is explicitly documented as intentionally legacy-only.

## FINAL CERTIFICATION — ANSWERS TO THE 13 REQUIRED QUESTIONS

1. **Is the pure pedagogical engine correct?** Mostly, but not fully — 3 of the audit's 4 BLOCKER findings (AUDIT-001/002/003) live entirely inside the pure engine.
2. **Is the full execution chain correct?** The server-authority/contract-enforcement layer (session start, generate-and-take, prepared-activity cache) is correct and well-tested; the migration/legacy-recognition layer (AUDIT-004) is not.
3. **Can every stage be entered and exited correctly?** No — PRACTICE can be exited (into PROVE) one attempt too early (AUDIT-001), and RETAIN's exit-on-failure path is wrong (AUDIT-002).
4. **Can every rollback recover correctly?** No — the RETAIN two-strike recovery (AUDIT-002) and the TRANSFER Case B recovery (AUDIT-003) are both missing.
5. **Can evidence be misclassified?** Not by the pure engine's own qualification logic for the fields it reads (verified extensively). It CAN be over-attributed at the migration layer (AUDIT-004).
6. **Can overlays corrupt canonical activity type?** No — verified: REINFORCE tagging (`metadata.canonicalActivityType`) has zero effect on qualification, since no code reads it for that purpose. This is currently safe by absence of a reader, not by a designed invariant — now protected by a regression-guard test.
7. **Can legacy data incorrectly satisfy v1 policy?** **Yes, structurally** (AUDIT-004) — though not yet exercised against real data.
8. **Can UI contradict canonical backend state?** Not confirmed for ConceptMission/Today (both correctly implement the One-Authority-Rule override); **unresolved** for `canonical-learning-progress.ts`'s consumers (AUDIT-006).
9. **Can wait windows be bypassed or restarted incorrectly?** The 3-day Retain gate itself is correctly enforced and correctly resets only on a new qualifying Prove. However, RETAIN's own broken two-strike logic (AUDIT-002) causes a **worse-than-specified** outcome (forced full Prove rebuild) rather than a bypass.
10. **Can a learner become permanently trapped?** No mechanism found that permanently traps a learner — every rollback path (correct or incorrectly-scoped) still leads to a requalification path.
11. **Can a learner advance too early?** **Yes** — AUDIT-001 (PROVE unlocked after a single Practice pass) is exactly this.
12. **Can a learner be forced to repeat unnecessary waiting/rebuilding?** **Yes** — AUDIT-002's core failure mode is exactly this (an unnecessary full Prove rebuild after what should be an immediate-retry Retain failure).
13. **Is the implementation ready for renewed manual E2E testing?** **Not yet**, specifically for PRACTICE-satisfaction and RETAIN-retry manual testing (AUDIT-001/002 will produce visibly wrong session behavior the instant `CANONICAL_ENGINE_V1_ENABLED=true` is set in a test environment). TRANSFER Case-B testing is not currently reachable anyway (no real per-challenge evidence source exists yet), and legacy-migration testing should be blocked entirely until AUDIT-004 is resolved, given the CLI's own `--apply` mode is a one-way write.

**No BLOCKER/P0 finding is waived.** Per the task's own certification rule, this yields **FAIL**, not `PASS_WITH_CONDITIONS`.

See [CANONICAL_GAPS_FOR_REMEDIATION.md](CANONICAL_GAPS_FOR_REMEDIATION.md) for the consolidated, fix-ready gap list. No remediation was implemented in this phase.
